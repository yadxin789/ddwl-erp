## 3 计算口径（`MrpService`）

| 项 | 规则 |
|---|---|
| 销售需求 | `sales_orders.status ∈ confirmed/picking/shipped`，未交量 = `line.qty - line.shipped_qty`，需求日取销售单 `delivery_date` |
| 工单需求 | `production_orders.status ∈ planned/released/in_progress` 且 **`sales_order_id` 为空**（独立备货工单）；剩余 = `plan_qty - completed_qty - defective_qty`，需求日取 `end_date` |
| 防重复 | 关联销售订单的工单不再计入（否则"销售单 + 它的工单"会算两遍） |
| BOM 展开 | 按 `product_material_id` 找最新 `status=active` 的 BOM；子件用量 × 需求 × `(1+loss_rate/100)`；跳过 `is_alternative=1`（替代料不并算）；多层递归，深度上限 8，带循环检测（命中写 warning 并截断） |
| 叶子判定 | 没有 active BOM 的物料就是采购件，累加毛需求 |
| 可用 | `inventory_stock.status='available'` 的 `SUM(qty - reserved_qty)`，**全公司合计**（MRP 是计划视角，不看部门行级范围） |
| 在途 | `purchase_orders.status ∈ draft/confirmed` 的 `SUM(qty - received_qty)` |
| 净需求 | `max(0, 毛需求 - 可用 - 在途)`，保留 2 位 |
| 供应商 | 该物料最近一张采购订单的供应商；无则空（页面显示"未指定"） |
| 需求日 | 同一物料多个来源时取最早 |

## 5 本轮抓到的一个存量真 bug

`PurchaseController` 把 `NumberGenerator` 的命名空间写成了 `App\Services\NumberGenerator`（真实是 `App\Support\NumberGenerator`）——**采购申请创建接口一旦被调用就是 500**（`Class not found`）。MRP 转申请正好走到同一段代码才暴露。已一并把 `PurchaseController` 与 `ProcurementController` 的 import 改成 `App\Support\NumberGenerator`。

## 7 未做 / 边界

- **只做采购建议，不做生产建议**：计划里的 MRP 只要求缺料→采购建议；自制半成品的"建议开工单/建议生产量"未做（APS 排程也仍属后续）。
- **可用库存不减 QC 隔离/不良**：只认 `available`，`qc_hold/blocked` 不计入可用（这是有意的保守口径，但没有在页面写"QC 待检不算可用"的说明，仅代码注释）。
- **在途只认采购订单**：采购申请（未转订单）、在制工单的预计产出都不算在途；因此"已提申请未下单"的缺口会重复出现在建议里，需要采购自己判断。
- **BOM 选择取最新 active**：同一成品存在多个 active BOM 时只展开 id 最大的那个，不做"按生效日/版本"择优；BOM 里的替代料整行跳过，不按替代比例分摊。
- **不处理已有建议的增量**：重新计算是"全量清空 open 再重建"，不是差异更新；如果采购已经人工改过建议数量，会被覆盖。
- **供应商按最近采购单推断**，不是物料主数据的默认供应商（材料表没有该字段）；新物料第一次采购会显示"未指定"。
- 建议转申请是 **1 建议 = 1 申请**，没有按供应商/需求日合并成一张多行申请。
- MRP 页面按建议逐条渲染，未分页（净需求行数量受 BOM 叶子数限制，演示量级可接受）。
- 时间口径只用"需求日"，没有按周分桶/时间分段净需求（time-phased MRP 未做）。
