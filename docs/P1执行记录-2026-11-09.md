审批流（§9.2）：

| business_type | 节点 | 通过后 |
|---|---|---|
| `purchase_order.confirm` | 采购主管（`pur-manager`）主审，总经理（`gm`）代批 | 订单 → confirmed；payload `action=close` 时 → closed |
| `stocktake.adjust` | 仓库主管（`wh-supervisor`），总经理代批 | 调 `InventoryAdjustmentService::approve()`，库存变动 + 流水 |

| `invoice.issue` | 会计 → 总经理 | 发票 `pending_approval` → `unpaid`（此时才计应收） |

| `sales_return.approve` | 销售主管（`sal-manager`） | 库存 available → returned，退货单 pending → received |

## 3. 引擎规则（`app/Services/ApprovalService.php` 重写）

| 规则 | 实现 |
|---|---|
| 申请人 ≠ 审批人 | `start()` 遇到"本步骤审批人 = 申请人"时：① 该步骤有非本人的代批人 → 保留（等代批人审）；② 没有 → 跳到下一级；③ 后面也没有 → 抛 `DomainException`，不生成"自己批自己"的实例 |
| 自批硬拒 | `decide()` 第一道校验：`actor === applicant_id` 直接拒绝（代批人也不许代自己） |
| 越权校验 | 只认本步骤 `approver_id` 或 `delegate_ids`，其余一律拒绝并写 `Log::warning` |
| 代批留痕（D-21） | 代批必须写理由（`InvalidArgumentException`）；日志条目记 `actor_id` + `delegated=true`；实例 `delegated=true`；通过代批写 `audit_logs` 的 `action=approval.approve` |
| 月度代批占比告警 | `warnIfDelegateRatioTooHigh()`：当月已批实例中 `delegated=true` 占比 > **30%** 写 `Log::warning`（`delegate_alert`） |
| 审批期间业务不执行 | `start()` 只挂实例；业务动作集中在 `apply()`，仅在最终通过后执行 |
| 待我审 | `canDecide()` + `pendingForUser()`：当前步骤主审人/代批人可见，申请人本人与无关岗位看不到；`ApprovalController::index` 改为走它 |
| 审计 | 通过/驳回/中间级通过都写 `audit_logs`（表不存在时降级为日志，不阻断业务） |

## 4. 接线改动

| 文件 | 改动 |
|---|---|
| `PurchaseController` | `orderConfirm` / `orderClose` 先 `start('purchase_order.confirm', …, ['action'=>…])`；有流则只挂审批（订单仍 draft），无流才直接调用服务 |
| `FinanceController` | `invoiceStore` 有流时先建 `pending_approval` 发票再挂审批（发起失败回滚删除）；`paymentStore` 有流时建 `pending` 收付款再挂审批；新增 `paymentExecute()`，**只有 `approved` 才能 → `executed`** |
| `SalesController::returnStore` | 退货单创建后挂 `sales_return.approve`；无流时直接 `apply()` |
| `RndController::extensionStore` | 延期申请挂 `rnd.extension` |
| `SalesReturnService` | `create()` 不再直接动库存（原来"先动库存再审批"等于审批摆设）；新增 `apply()` 在审批后做 available → returned，幂等 |
| `RndProjectService` | 新增 `approveExtension()`：顺延 `end_date`、复位 `is_overdue`、累计 `extension_days`，幂等 |
| `InventoryAdjustmentService` | 超阈值调整额外 `start('stocktake.adjust')` 让审批中心可见；库存调整页直接审批时 `syncApprovalInstance()` 把实例一并收口 |
| `routes/web.php` | 新增 `POST /finance/payments/{payment}/execute`（`finance.payments.execute`，`whereNumber`，仅出纳执行权） |

## 5. 顺带修掉的三个真 bug（此前被"空表单校验先返回 302"掩盖）

1. **`FinanceController` 的 `NumberGenerator` 命名空间写错**（`App\Services\NumberGenerator`，实际在 `App\Support`）——发票一填真实数据创建就 500；以前测试只 POST 空表单，被校验拦下返回 302，所以从未暴露。
2. **`Payment` 模型 `$fillable` 缺 `status`**——新增列后状态更新被 Eloquent 静默丢弃，"执行付款"永远不生效。
3. **`ApprovalInstance` `$fillable` 未含新列**——`delegated` / `payload_json` / `approved_at` 写不进去，代批标记形同不存在（测试直接抓到）。

| 检查 | 结果 |
|---|---|
| `php artisan migrate` | `000003_add_approval_delegate_fields` DONE、`000004_create_audit_logs_table` DONE |

| `php artisan erp:guard:check` | 权限库 **147**；M1~M7 全部通过 |

`ApprovalFlowTest` 覆盖：
1. 6 条流已种子且审批人/代批人可解析（采购主管+总经理代批、付款/发票两级会计→总经理）。
2. 审批节点岗位权限已授予；申请人侧岗位没有对应审批权；执行付款路由只挂出纳执行权。
3. 主管提交确认 → 订单仍 `draft`；主管自批被拒；无关岗位越权被拒；总经理代批后 `confirmed` 且写 `audit_logs`。
4. 代批不写理由失败、写理由通过且实例 `delegated=true`。
5. 审批中心只显示"待我审"（申请人自己看不到，仓管看不到，代批人能看到）。
6. 会计开票 → `pending_approval`，实例直接停在总经理一级（会计是制单人不能自审），总经理批后才 `unpaid`。
7. 付款 `pending` 时出纳执行被拒，`approved` 后才可 `executed`。

## 7. 本轮未做 / 边界（写清，避免"假验收"）

- **付款制单入口仍挂在出纳**（`POST /finance/payments` 原有路由权限 `finance.payment.execute` 未动）。计划 §9.2 写的是"会计制单"，要真正拆开需要新增会计侧"付款申请"入口与权限，属 P1-03（财务核销）一起做，本轮只保证"未批不得执行"。
- **研发延期与客户退货的接线没有单独写测试**（代码已接，`ApprovalFlowTest` 未造这两类数据）；P1-05（研发 PLM）会自然覆盖延期，P1-04 主流程覆盖退货。
- **库存调整双路径**：库存调整页自己审批（原有 `inventory.adjust.approve` 按钮）与审批中心审批并存，两处都幂等并互相同步；统一直到 P1-04 主流程重构时再收口为单一路径。
- **代批 30% 告警只写日志**（`Log::warning`），没有告警通知渠道（系统无消息中心分级），P2 评估是否接通知。
